A low-balance alert is only useful if it arrives while there are still credits left. When the ongoing balance refreshes on a periodic cycle, a fast workload can drain a wallet and go negative before the alert fires.

Real-time alerts close that gap. Lago evaluates your [credits consumption alerts](/guide/alerts/credits-consumption-alerts) on the same refresh that updates the wallet's ongoing balance, within about 2 seconds of the event.

## What changes

| | Without the add-on | With real-time alerts |
| --- | --- | --- |
| Ongoing balance refresh | Periodic cycle | Within about 2 seconds of each event |
| Alert evaluation | On the next periodic check | On the same refresh as the balance |
| Burst of events | Evaluated on the next check | One evaluation per wallet per refresh, one alert |
| Alerts, thresholds, webhooks | Unchanged | Unchanged |

Nothing changes in how you create alerts or consume webhooks. The add-on changes when alerts are evaluated, not what they are.

## How it works

<Steps>
  <Step title="An event arrives">
    You send a usage event as usual. Lago adds it to the customer's usage as it streams in.
  </Step>
  <Step title="The ongoing balance refreshes">
    Within about 2 seconds, the wallet's ongoing balance reflects the event. A burst of events produces a single refresh per customer.
  </Step>
  <Step title="Alerts are evaluated">
    Lago evaluates the wallet's alerts against the new balance. Wallets with no alerts, and refreshes that leave the balance unchanged, are skipped.
  </Step>
  <Step title="The webhook is sent">
    When a threshold is crossed, Lago creates the triggered alert and sends `alert.triggered`. Alert webhooks run on their own worker, so they are not queued behind other webhook traffic.
  </Step>
</Steps>

## Which alerts are evaluated in real time

Real-time evaluation applies to credits consumption alerts on wallets whose ongoing balance is refreshed in real time:

- **Wallet ongoing balance amount** (`wallet_ongoing_balance_amount`)
- **Wallet ongoing balance credits** (`wallet_credits_ongoing_balance`)

The ongoing balance is refreshed in real time for usage from [covered charges](/guide/events/real-time-usage#coverage). Usage from other charges reaches the balance on the periodic refresh, and alerts on it fire then.

Balance alerts (`wallet_balance_amount`, `wallet_credits_balance`) follow the wallet balance, which moves on invoices, top-ups and voids rather than on each event. [Usage alerts](/guide/alerts/usage-alerts) keep their existing schedule.

## Set up a real-time alert

Once the add-on is enabled, create an alert on the ongoing balance exactly as you would without it. Give each threshold a `code` that maps to the action your product takes.

```bash Create a real-time low-balance alert
LAGO_URL="https://api.getlago.com"
API_KEY="__YOUR_API_KEY__"

curl --location --request POST "$LAGO_URL/api/v1/customers/:customer_external_id/wallets/:wallet_code/alerts" \
  --header "Authorization: Bearer $API_KEY" \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "alert": {
      "alert_type": "wallet_credits_ongoing_balance",
      "code": "low_credits",
      "name": "Low credits",
      "thresholds": [
        { "code": "warning", "value": "500", "recurring": false },
        { "code": "critical", "value": "50", "recurring": false },
        { "code": "empty", "value": "0", "recurring": false }
      ]
    }
  }'
```

Then listen for `alert.triggered`. The payload is the same as for any [credits consumption alert](/guide/alerts/credits-consumption-alerts#alert-notifications). Use the threshold `code` to decide what your product does: warn on `warning`, restrict on `critical`, block or top up on `empty`.

To also know when the balance is back above a threshold, for example after a top-up, opt the threshold in to [alert resolution](/guide/alerts/alert-resolution).

## Good to know

- **Lago notifies, your product enforces.** The alert tells you a threshold was crossed. Blocking, throttling or topping up happens in your application or gateway.
- **Not a spending cap.** Requests served between the event and your reaction still consume credits, and the ongoing balance can go below zero. To enforce a hard limit, authorize the work in your application before it starts.
- **Automatic fallback.** If the real-time refresh is delayed, the periodic refresh updates the balance and evaluates the alerts. No threshold crossing is lost.
- **Same rules as other alerts.** Decreasing thresholds, the 20-threshold limit and evaluation only after the alert is created all apply. See the [limitations](/guide/alerts/credits-consumption-alerts#limitations).
