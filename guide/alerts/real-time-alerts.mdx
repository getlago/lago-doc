An alert is only useful if it arrives while you can still act on it. When usage and balances refresh on a periodic cycle, a fast workload can blow through a budget or drain a wallet before the alert fires.

With real-time alerts, Lago evaluates your alerts as usage streams in. The `alert.triggered` webhook reaches you from under a second to a few seconds after the event that crossed the threshold.

## What changes

| | Without the add-on | With real-time alerts |
| --- | --- | --- |
| Alert evaluation | Periodic | As usage streams in |
| Time to `alert.triggered` | Up to minutes | Under a second to a few seconds |
| Alerts, thresholds, webhooks | Unchanged | Unchanged |

It applies to all your alerts, [usage alerts](/guide/alerts/usage-alerts) and [wallet alerts](/guide/alerts/credits-consumption-alerts) alike. Nothing changes in how you create alerts or consume webhooks. The add-on changes when alerts fire, not what they are.

## How it works

<Steps>
  <Step title="An event arrives">
    You send usage events as usual. Lago aggregates them as they stream in.
  </Step>
  <Step title="Usage and balances refresh">
    Current usage and wallet ongoing balances reflect the event within seconds.
  </Step>
  <Step title="Alerts are evaluated">
    Lago checks your alerts against the new values. A burst of events triggers one alert, not one per event.
  </Step>
  <Step title="Your product acts">
    You receive `alert.triggered` and decide what happens: warn, throttle, block or top up.
  </Step>
</Steps>

## Set up a real-time alert

Once the add-on is enabled, create alerts exactly as you would without it. Give each threshold a `code` that maps to the action your product takes.

```bash Create a low-credits alert
LAGO_URL="https://api.getlago.com"
API_KEY="__YOUR_API_KEY__"

curl --location --request POST "$LAGO_URL/api/v1/customers/:customer_external_id/wallets/:wallet_code/alerts" \
  --header "Authorization: Bearer $API_KEY" \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "alert": {
      "alert_type": "wallet_credits_ongoing_balance",
      "code": "low_credits",
      "name": "Low credits",
      "thresholds": [
        { "code": "warning", "value": "500", "recurring": false },
        { "code": "critical", "value": "50", "recurring": false },
        { "code": "empty", "value": "0", "recurring": false }
      ]
    }
  }'
```

Then listen for `alert.triggered`, with the same payload as any other alert: warn on `warning`, restrict on `critical`, block or top up on `empty`. Usage alerts work the same way, on increasing thresholds. To also know when a value is back on the safe side, use [alert resolution](/guide/alerts/alert-resolution).

## Good to know

- **Lago notifies, your product enforces.** Blocking, throttling or topping up happens in your application or gateway.
- **Not a spending cap.** Usage served before your product reacts is still consumed, and a balance can go below zero. To enforce a hard limit, authorize the work in your application before it starts.
- **Automatic fallback.** If the real-time path is delayed, alerts are evaluated on the periodic cycle. No threshold crossing is lost.
- **Coverage follows real-time usage.** Alerts on charges that are not [covered](/guide/events/real-time-usage#coverage) by the add-on fire on the periodic cycle.
