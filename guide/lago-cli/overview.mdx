The [Lago CLI](https://github.com/getlago/lago-cli) is the official command-line interface for Lago. It is generated from the Lago OpenAPI specification, so every resource in the [API reference](/api-reference/intro) has a command, and it ships as one static Go binary with no runtime dependencies.

It works against Lago Cloud US, Lago Cloud EU, and self-hosted instances.

<Note>
  The CLI is under active development. Until the first signed release, use a test profile (`--mode test`) rather than a live one.
</Note>

## Install

Two channels are supported. Both are smoke-tested on every release.

<CodeGroup>

```bash Homebrew
brew install getlago/tap/lago
```

```bash Go
# Requires Go 1.27 or newer
go install github.com/getlago/lago-cli/cmd/lago@latest
export PATH="$(go env GOPATH)/bin:$PATH"
```

</CodeGroup>

Release archives are built for macOS, Linux, and Windows on amd64 and arm64. `go install` works anywhere Go runs, Windows included.

Check the install:

```console
$ lago version
GO_VERSION    go1.27.0
PLATFORM      darwin/arm64
SPEC_SHA256   852e7331acfc080d1af9bda9d1663a50a7fa5b4a2aea22a89fb16787ee75b671
SPEC_VERSION  1.52.1
VERSION       1.0.0
```

`SPEC_VERSION` is the Lago OpenAPI version the binary was generated from. It tells you which API fields and endpoints the CLI knows about.

<Tip>
  If `type -a lago` reports an alias or a shell function, that definition shadows the binary. Lago contributors often have a `lago` alias pointing at a Docker Compose helper. Remove it or rename it to `lago-dev` before using the CLI.
</Tip>

### Shell completion

```bash
# zsh
lago completion zsh > ~/.zfunc/_lago

# bash
lago completion bash > /etc/bash_completion.d/lago

# fish
lago completion fish > ~/.config/fish/completions/lago.fish

# PowerShell
lago completion powershell | Out-String | Invoke-Expression
```

### Upgrade

The CLI never replaces itself. `lago upgrade` checks for a newer release and prints the command that matches how the binary was installed:

```console
$ lago upgrade
Lago CLI 1.1.0 is available (installed: 1.0.0).

    brew upgrade getlago/tap/lago
```

For a `go install` binary it prints the `go install ...@latest` command instead.

## Configure

Create an API key in the Lago app under **Developers > API keys**, then point the CLI at the API host for your deployment.

| Deployment | Dashboard | `--api-url` | `--region` |
| --- | --- | --- | --- |
| Lago Cloud US | `https://app.getlago.com` | `https://api.getlago.com` | `us` |
| Lago Cloud EU | `https://app.eu.getlago.com` | `https://api.eu.getlago.com` | `eu` |
| Self-hosted | your host | your API base URL, for example `https://lago.example.com` | `self-hosted` |

### Create a profile

`lago init` validates the key against `GET /api/v1/organizations` before writing anything. A saved profile is a validated profile.

<CodeGroup>

```bash Cloud US
lago init --api-key "$LAGO_API_KEY" --region us --mode test
```

```bash Cloud EU
lago init --api-key "$LAGO_API_KEY" --region eu --mode test
```

```bash Self-hosted
lago init --api-key "$LAGO_API_KEY" --region self-hosted --api-url https://lago.example.com --mode test
```

```bash Named profile
lago init --profile staging --api-key "$LAGO_API_KEY" --region eu --mode test
lago --profile staging customers list
```

</CodeGroup>

```console
$ lago init --api-key "$LAGO_API_KEY" --region us --mode test
Connected to Lago as Example Organization.
Saved us profile "default" to ~/.config/lago/config.toml (mode: test).
```

A wrong key persists nothing and exits with code 3.

The config file lives at `~/.config/lago/config.toml` on macOS and Linux and `%AppData%\lago\config.toml` on Windows. It is written with mode `0600` and is the only place the CLI persists an API key. Override the location with `LAGO_CONFIG_FILE`.

### Pass the base URL

Configure the **base** URL. The CLI appends `/api/v1` itself. These inputs all normalize to the same host:

- `https://api.getlago.com`
- `https://api.getlago.com/api/v1` (the full path pasted from the API reference)
- `https://api.getlago.com/` (trailing slash)
- `https://lago.example.com:8443` (custom port, preserved)
- `https://tools.example.com/lago` (sub-path behind a proxy, preserved)

The app URL is refused by name. `https://app.getlago.com` is the dashboard, not the API. It answers HTTP requests, which is what makes the mistake confusing, so the CLI stops before sending your key anywhere:

```console
$ lago init --api-key "$LAGO_API_KEY" --api-url https://app.eu.getlago.com
Error: app.eu.getlago.com is the Lago dashboard, not the Lago API
Suggestion: Use https://api.eu.getlago.com instead. The API and the app are different hosts, and an API key sent to the app host will not authenticate.
```

Plain HTTP requires `--insecure` and always prints a warning. Use it for `http://localhost:3000` during development, not against an instance that holds real money.

### Check what you are hitting

`whoami` shows the profile and the resolved host. `API_URL` is what the profile holds. `RESOLVED_API_URL` is the base URL requests go to.

```console
$ lago whoami
API_URL           https://api.eu.getlago.com
MODE              test
ORGANIZATION      {"organization":{"lago_id":"org_...","name":"Example Organization"}}
PROFILE           default
REGION            eu
RESOLVED_API_URL  https://api.eu.getlago.com/api/v1
```

`lago doctor` runs configuration, permission, network, and authentication checks and reports the same resolved URL. It separates "wrong credentials" from "right credentials, wrong host", and it is the first thing to paste into a support ticket.

```bash
lago doctor
lago doctor --output json --query 'checks[].{check: name, detail: detail}'
lago doctor --bundle   # writes a sanitized diagnostic archive
```

### Precedence

Configuration resolves flags, then environment variables, then the selected profile.

| Setting | Flag | Environment variable |
| --- | --- | --- |
| API URL | `--api-url` | `LAGO_API_URL` |
| API key | `--api-key` | `LAGO_API_KEY` |
| Mode | `--mode` | `LAGO_MODE` |
| Profile | `--profile` | `LAGO_PROFILE` |
| Timeout | `--timeout` | `LAGO_TIMEOUT` |
| Config file | | `LAGO_CONFIG_FILE` |
| Update check | | `LAGO_NO_UPDATE_CHECK=1` disables it |

Environment variables suit CI and one-off shells:

```bash
export LAGO_API_KEY="..." LAGO_API_URL="https://api.getlago.com" LAGO_MODE="test"
lago customers list
```

### Live and test mode

Mode is a CLI-side safety declaration. Lago has no server-side sandbox, so `--mode test` does not make data synthetic. It changes how the CLI behaves:

- **Live** commands print `[LIVE]` on stderr.
- **Live** destructive operations require the resource identifier via `--confirm`, or a typed confirmation in an interactive terminal.

**Mode defaults to live.** A credential override (`--api-key`, `--api-url`, `LAGO_API_KEY`, `LAGO_API_URL`) without an explicit mode resolves to live, not test. A script that forgets `--mode` gets the confirmation gates rather than a silent write to production.

<Warning>
  Your organization on Lago Cloud is real. Before running anything from this page against it, confirm it holds no production customers, or use a dedicated test organization. Prefix everything you create (`qa_`, `demo_`) so you can find and delete it afterwards.
</Warning>

## Quickstart

A metric, a plan, a customer, a subscription, one usage event, and an invoice preview. Every command below runs against your configured profile.

<Steps>

<Step title="Create a billable metric">

```console
$ lago billable-metrics create --name Requests --code quickstart_requests --aggregation-type count_agg
LAGO_ID  0b8a1e70-1a90-4b2c-9f3d-5e6a7b8c9d01
CODE     quickstart_requests
NAME     Requests
```

</Step>

<Step title="Create a plan with a charge on that metric">

The `billable_metric_id` is the `LAGO_ID` from the previous step. Nested payloads take `--input` with inline JSON or `@file.json`.

```console
$ lago plans create --input '{"plan":{"name":"Quickstart","code":"quickstart","interval":"monthly","amount_cents":0,"amount_currency":"USD","pay_in_advance":false,"charges":[{"billable_metric_id":"0b8a1e70-1a90-4b2c-9f3d-5e6a7b8c9d01","charge_model":"standard","properties":{"amount":"1"}}]}}'
LAGO_ID  2b902b90-2b90-2b90-2b90-2b902b902b90
CODE     quickstart
NAME     Quickstart
```

</Step>

<Step title="Create a customer">

```console
$ lago customers create --external-id quickstart_customer --name "Quickstart Customer" --currency USD
LAGO_ID      1a901a90-1a90-1a90-1a90-1a901a901a90
EXTERNAL_ID  quickstart_customer
NAME         Quickstart Customer
```

</Step>

<Step title="Assign the plan">

```console
$ lago subscriptions create \
    --subscription-external-customer-id quickstart_customer \
    --subscription-external-id quickstart_subscription \
    --subscription-plan-code quickstart
LAGO_ID      3c903c90-3c90-3c90-3c90-3c903c903c90
EXTERNAL_ID  quickstart_subscription
```

</Step>

<Step title="Send a usage event">

A transaction ID is generated when you omit one. Events are idempotent on `transaction_id`: sending the same one twice never double-bills.

```console
$ lago events send --external-subscription-id quickstart_subscription --code quickstart_requests
CODE            quickstart_requests
LAGO_ID         5e905e90-5e90-5e90-5e90-5e905e905e90
TRANSACTION_ID  0f3c1d2e-4a5b-6c7d-8e9f-0a1b2c3d4e5f
```

</Step>

<Step title="Preview the invoice">

```console
$ lago invoices preview --input '{"customer":{"external_id":"quickstart_customer"},"subscriptions":{"external_ids":["quickstart_subscription"]}}'
CURRENCY            USD
FEES                [{"amount_cents":100,"units":"1.0"}]
ISSUING_DATE        2026-10-01
TOTAL_AMOUNT_CENTS  100
```

</Step>

</Steps>

`lago seed demo` runs this whole chain in one command with a `demo` prefix. `lago fixtures run scenario.yaml` runs your own multi-step scenarios with variable capture between steps. Both are covered in the [command reference](/guide/lago-cli/commands#seed-and-fixtures).

## Output

Three formats, selected with `--output` or `-o`: `table` (default), `json`, `yaml`.

### Creates and updates print identifiers

Every `create` and `update` prints a terse identifier block by default: `lago_id`, `external_id`, `code`, and `name`, whichever the resource carries. After a create, the one thing you do not already have is the ID Lago minted.

`--output json` returns the complete resource, and that is the form to script against:

```console
$ lago customers create --external-id quickstart_customer --name "Quickstart Customer" --output json
{
  "customer": {
    "lago_id": "1a901a90-1a90-1a90-1a90-1a901a901a90",
    "external_id": "quickstart_customer",
    "name": "Quickstart Customer",
    "currency": "USD",
    "created_at": "2026-09-01T10:00:00Z"
  }
}
```

Reads (`get`, `list`) print every column. Read-shaped mutations (`invoices preview`, `credit-notes estimate`), state transitions (`invoices finalize`, `invoices void`), and bulk ingestion (`events send --file`) are not reduced either.

### Money is exact

Amounts in minor units (`*_amount_cents`) are integers. Fractional values such as `units` are decimal strings (`"42.0"`). The CLI never emits a floating-point monetary field. Compare `total_amount_cents` from the CLI with the dashboard and they match.

## Query responses with `--query`

`--query` takes a [JMESPath](https://jmespath.org) expression and applies it to the response.

**Lago wraps every response**, and the wrapper is part of the path. A query written against the unwrapped resource matches nothing.

| Command | Response shape | Query starts with |
| --- | --- | --- |
| `customers get` | `{"customer": {...}}` | `customer.` |
| `customers list` | `{"customers": [...], "meta": {...}}` | `customers[` |
| `subscriptions get` | `{"subscription": {...}}` | `subscription.` |
| `invoices list` | `{"invoices": [...], "meta": {...}}` | `invoices[` |
| `customers current-usage` | `{"customer_usage": {...}}` | `customer_usage.` |

```console
$ lago customers get quickstart_customer --output json --query 'customer.email'
"billing@example.com"

$ lago invoices list --output json --query 'invoices[?status==`"finalized"`].{id: lago_id, total: total_amount_cents}'
[
  {
    "id": "4d904d90-4d90-4d90-4d90-4d904d904d90",
    "total": 150000
  }
]
```

A JMESPath backtick literal holds JSON, so a string comparison needs inner double quotes: `` `"finalized"` `` works, bare `` `finalized` `` is rejected as an invalid query. The alternative is the raw-string form with single quotes, which means double-quoting the whole expression for your shell:

```bash
lago invoices list --output json --query "invoices[?status=='finalized'].[lago_id]"
```

When a query matches nothing, stdout still prints `null` so script parsing does not change, and stderr names the keys that were available:

```console
$ lago customers list --output json --query 'lago_id'
query matched nothing; top-level keys: customers, meta
null
```

`--query` without `--output` switches to JSON and says so. An explicit `--output` always wins, `--output table` included.

```console
$ lago customers list --query 'customers[].external_id'
--query implies --output json; pass --output table explicitly to render the result as a table.
[
  "quickstart_customer"
]
```

## Pagination and filters

Every `list` command exposes the endpoint's query parameters as flags. Filter flags map one-to-one to the API's query parameters, so the [API reference](/api-reference/intro) for an endpoint is the reference for its `list` flags.

```bash
lago invoices list --statuses finalized --payment-statuses pending --external-customer-id quickstart_customer
lago customers list --search-term acme --countries FR,DE
lago events list --external-subscription-id quickstart_subscription --timestamp-from 2026-09-01T00:00:00Z
lago fees list --fee-type charge --created-at-from 2026-09-01
```

| Flag | Effect |
| --- | --- |
| `--limit N` | Sets `per_page`. Returns one page of at most N records. |
| `--page N` | Requests page N. |
| `--per-page N` | Same as `--limit`, matching the API parameter name. |
| `--all` | Fetches every page from `--page` (default 1) onwards, 100 records per page, and renders each page as it arrives. |
| `--watch` | Re-runs the request every `--watch-interval` (default `2s`, minimum `500ms`) and re-renders when the response changes. |

`--all` streams pages without buffering the whole collection, so it is the scale-safe form. Each page is one wrapped JSON document, which is what to feed `jq`:

```bash
lago customers list --all --output json \
  | jq -r '.customers[] | select(.external_id | startswith("qa_")) | .external_id'
```

`--all` and `--query` are mutually exclusive. A whole-collection JMESPath expression has nothing to evaluate against when pages stream. Use a per-page `--query` without `--all`, or the `jq` form above.

## Dry run

`--dry-run` prints the request a mutating command would send, and sends nothing. No connection is opened, so it works with a dead API URL.

```console
$ lago customers create --external-id qa_dry_001 --name "Dry Run Co" --currency USD --dry-run
BODY     {"customer":{"currency":"USD","external_id":"qa_dry_001","name":"Dry Run Co"}}
HEADERS  {"Accept":["application/json"],"Authorization":["Bearer [REDACTED]"],"Content-Type":["application/json"],"User-Agent":["lago-cli/1.0.0"]}
METHOD   POST
URL      https://api.getlago.com/api/v1/customers
```

The API key is redacted from dry runs, error output, and `--verbose` logs. The body is the exact wrapped payload the API receives, so a dry run is the fastest way to check how flags map to the request schema before touching real data.

## Safety gates

Danger is derived from the API path, not the HTTP verb. `PUT /invoices/{id}/finalize` is idempotent by RFC but irreversible by accounting. Any operation matching the destructive vocabulary (`void`, `finalize`, `retry`, `terminate`, `delete`, `destroy`, `refund`) or using `DELETE` is confirmation-gated.

In a terminal you type the identifier. In a script, pass it with `--confirm`:

```console
$ lago customers delete qa_cust_001 < /dev/null
Error: confirmation required for qa_cust_001
Suggestion: Pass --confirm "qa_cust_001" or rerun in an interactive terminal.
$ echo $?
2

$ lago customers delete qa_cust_001 --confirm qa_cust_001
```

A wrong value in `--confirm` is refused the same way. The identifier has to match.

### Retries and idempotency

Retries apply only to network errors, HTTP 429, and 5xx responses. They run only for idempotent methods (`GET`, `HEAD`, `OPTIONS`) or when a request carries an idempotency key. `Retry-After` is honored, then exponential backoff with jitter. `--no-retry` disables them.

Every mutation accepts `--idempotency-key`, which sets the `Idempotency-Key` header and makes the request safe to retry:

```bash
lago payments create --invoice-id 4d904d90-... --amount-cents 150000 --reference wire-2026-09 --idempotency-key wire-2026-09
```

For bulk events, each NDJSON line gets a transaction ID if it lacks one, and is sent with a matching idempotency key. The input file is streamed, never loaded into memory.

```bash
lago events send --file events.ndjson --concurrency 8
cat events.ndjson | lago events send --file -
```

## Raw API access

`lago api` sends an authenticated request to any endpoint, with the same profile, redaction, retries, and output handling as the generated commands. Use it for endpoints newer than the CLI's embedded spec.

```bash
lago api GET /customers?page=2
lago api POST /events --data @event.json --idempotency-key event-42
printf '{"event":{...}}' | lago api POST /events --data -
lago api GET /api/v1/customers   # the /api/v1 prefix is stripped, not doubled
```

## Diagnostics

| Flag | What it does |
| --- | --- |
| `--verbose` | Prints request and response details with the key redacted. |
| `--timing` | Prints a latency breakdown: API round-trip, retry wait, CLI overhead. |
| `--timeout 30s` | Total request budget. Connect and TLS have a separate five-second budget. |
| `--no-retry` | Disables automatic retries. |

`lago logs tail` polls the API request logs and re-renders when they change, with filters on method, status class, and path:

```bash
lago logs tail --status 4xx --resource /customers --method POST
```

## Exit codes

Exit codes are stable. Changing this table is a breaking change.

| Code | Meaning |
| ---: | --- |
| 0 | Success |
| 1 | Generic error |
| 2 | Usage error (bad flag, missing confirmation, refused URL) |
| 3 | Authentication or authorization error |
| 4 | Not found |
| 5 | Validation or other API 4xx error |
| 6 | Rate limited |
| 7 | Lago server 5xx error |
| 8 | Network or timeout error |

Errors are structured. A 404 names the resource type and the value that was not found, which matters when an identifier is the wrong kind: a plan code passed where a subscription external ID was expected is not "no usage", it is "no such subscription".

```console
$ lago events send --external-subscription-id ai_plan_gpt4_tokens --code api_calls
Error: no subscription "ai_plan_gpt4_tokens" exists in this organization
Suggestion: Check that each identifier is the right kind for the flag it was passed to: a plan code is not a subscription external ID, and a Lago ID is not an external ID.
$ echo $?
4
```

## Global flags

Available on every command.

| Flag | Description |
| --- | --- |
| `--api-key` | Override the API key. |
| `--api-url` | Override the API base URL. |
| `--profile` | Named profile from the config file. |
| `--mode live\|test` | Environment mode. Defaults to live when credentials are overridden. |
| `--confirm <identifier>` | Confirm a dangerous operation with its resource identifier. |
| `--dry-run` | Print the request without sending it. |
| `--output`, `-o table\|json\|yaml` | Output format. |
| `--query <jmespath>` | JMESPath expression applied to the response. |
| `--insecure` | Allow plain HTTP or disabled TLS verification for self-hosted Lago. |
| `--timeout <duration>` | Total request timeout. Default `30s`. |
| `--no-retry` | Disable automatic retries. |
| `--timing` | Print the request latency breakdown. |
| `--verbose` | Print redacted request and response details. |

## Privacy

The CLI sends no product telemetry. With explicit consent given at `lago init --update-check`, it makes at most one anonymous release-metadata request per 24 hours. `LAGO_NO_UPDATE_CHECK=1` disables it.
