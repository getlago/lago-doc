Open your app's repository in your coding agent. Have it inspect your pricing, usage, and any billing you already run. Before it edits code, decide which system will calculate charges, issue invoices, and collect payments.

Then have the agent add the integration. Your app sends customers, subscriptions, and usage to Lago through an [SDK or REST API](/api-reference/intro). You can run local tests before you have a Lago organization. Once connected, use the [Lago CLI](/guide/lago-cli/overview) to configure Lago and read its recorded usage. Check it against your app's records. [Invoice preview](/guide/invoicing/previews) requires Premium.

## Choose your agent

| Agent | Open your application repository | Lago install path |
| --- | --- | --- |
| Claude Code | Run `claude` in the repository | [Plugin](https://github.com/getlago/lago-plugin#claude-code) |
| Codex | Run `codex` or open the repository in Codex | [Plugin](https://github.com/getlago/lago-plugin#codex) |
| GitHub Copilot CLI | Run `copilot` in the repository | [Plugin](https://github.com/getlago/lago-plugin#github-copilot-cli) |
| Gemini CLI | Run `gemini` in the repository | [Extension](https://github.com/getlago/lago-plugin#gemini-cli) |
| Cursor | Open the repository in Cursor Agent | [Plugin manifest](https://github.com/getlago/lago-plugin#cursor); not tested in Cursor |
| Other agents that support Agent Skills | Open the repository in your agent | [Skill-only install](https://github.com/getlago/lago-plugin#other-agents-with-agent-skills) |

The CLI and API workflow below does not require the plugin. [Local install checks](https://github.com/getlago/lago-plugin/tree/main/docs/release-evidence/agents-2026-10-19) verified the offline demo in GitHub Copilot CLI and Gemini CLI; they did not test automatic skill selection or a billing integration. Cursor's manifest is published but untested in Cursor. The Agent Skills route installs the skill without the bundled demo.

Connect the [documentation MCP](/guide/ai-agents/for-agents#give-your-agent-the-documentation) if you want your agent to look up Lago's current guides and API reference as it codes. It searches public docs; use the authenticated CLI in step 1 to inspect or configure your Lago organization.

## 1. Connect to the right Lago organization

For an offline first pass, skip to step 2 and return here before any live CLI request.

Before connecting the CLI, choose the Lago organization you will use:

- **Lago Cloud:** Accept the invitation from Lago or your team to a specific organization and sign in. Confirm whether that organization is in the US or EU region; the CLI setup below asks you to choose one. If you have no invitation, ask your Lago contact or organization admin for access.
- **Self-hosted Lago:** Use your team's existing deployment or [deploy Lago](/guide/lago-self-hosted/overview). Record the API service's base URL, or ask the operator for it: for example, `https://lago.example.com` (without `/api/v1`).

In that **same organization**, get an API key from **Developers → API keys**, or ask an admin to provide one. Expose it to your terminal as `LAGO_API_KEY`, directly or through a secret manager; keep it out of prompts and source control. Install the CLI in the development environment where you run your coding agent:

```bash
brew install getlago/tap/lago
lago version
```

On other systems, use the [CLI release archives](https://github.com/getlago/lago-cli/releases). Initialize one profile for your target:

<CodeGroup>

```bash Cloud US
lago init --api-key "$LAGO_API_KEY" --region us
```

```bash Cloud EU
lago init --api-key "$LAGO_API_KEY" --region eu
```

```bash Self-hosted
lago init --api-key "$LAGO_API_KEY" --region self-hosted \
  --api-url https://lago.example.com
```

</CodeGroup>

For self-hosted Lago, `--api-url` must point to the API service if its address differs from the web app. Confirm the organization and exact host before any write:

```bash
lago whoami
lago doctor
```

`--mode test` is a safety declaration, **not a sandbox**. A CLI dry run prints a request but sends nothing. For synthetic live exercises, use a dedicated, isolated self-hosted instance with no real customers or payment provider. Use a designated environment and your own actual pricing and customer data when validating a real Cloud integration. Do not seed generic demo data in a shared or production organization.

If your isolated instance uses loopback-only HTTP, add `--insecure` to each CLI command. The CLI requires it for HTTP. Keep the example's normal HTTPS configuration for any nonlocal deployment.

## 2. Get a first result without billing anyone

The public [growth-agent billing lab](https://github.com/anhtho-lago/growth-agent-billing-lab) is a small synthetic application for practicing the workflow. One existing customer has a flat monthly charge collected through Stripe Payments. Stripe is specific to this fixture. The fixture records a Stripe customer ID and monthly amount; it does not model the existing invoice or subscription system.

The application has durable usage records but starts without a Lago integration. Its [billing brief](https://github.com/anhtho-lago/growth-agent-billing-lab/blob/main/BILLING_BRIEF.md) describes a \$500 monthly plan, 50,000 included credits, and \$0.05 for each excess credit. The expected pretax amount at 75,000 credits is **\$1,750**.

```bash
git clone https://github.com/anhtho-lago/growth-agent-billing-lab.git
cd growth-agent-billing-lab
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

Open this repository in your chosen agent and paste its [credits-and-overage prompt](https://github.com/anhtho-lago/growth-agent-billing-lab/blob/main/prompts/credits-and-overage.md). Have the agent show its payer, event contract, IDs, ownership boundaries, and independent money calculation **before editing**. Then let it implement the smallest server-side adapter and offline tests. The agent should leave `legacy_zenith` on its existing flat-charge and Stripe Payments collection path.

**Expected offline result:** a code diff, tests for 50,000, 50,001, and 75,000 credits, and evidence that a retry reuses the source `transaction_id` and explicit `timestamp`. An offline pass is not a Lago invoice result.

## 3. Apply your application's billing design

In your own repository, use this prompt to begin with the business rule and current system ownership rather than an API call:

```text
Read https://getlago.com/llms.txt and the relevant Lago guides. Check
https://swagger.getlago.com/openapi.yaml for exact API fields.

Our customers pay for [describe your actual pricing]. Inspect this repository.
Before editing, show who pays; the durable customer, subscription, and source
usage IDs; and the product action that creates usage. Map which system currently
calculates charges, issues invoices, and collects payments. Identify existing
customers and any migration boundary. Propose what Lago should own, the metric
and plan, and one independent example bill. Distinguish code evidence from
assumptions, and ask about decisions that change money or ownership. Do not
change existing billing or payment paths or access a live Lago organization yet.
```

Review the proposed ownership and migration boundary before the agent edits code. The first integration can leave existing customers on their current path while you test a new cohort with Lago; a cutover needs an explicit plan for invoices, payments, and duplicate charges. Once you accept that design, ask the agent to implement server-side SDK or REST calls, retries, and offline money tests. The event's `transaction_id` must come from a durable source record. Persist its original timestamp so a retry uses **both** the same ID and timestamp; both matter for duplicate protection on ClickHouse-based event pipelines. See [idempotency and deduplication](/guide/events/ingesting-usage#idempotency-and-deduplication).

Have the agent write reviewable CLI requests for the metric and plan. Inspect existing configuration before creating anything:

```bash
lago billable-metrics list --limit 50
lago plans list --limit 50

# Illustrative metric; use your product's accepted code and aggregation.
lago billable-metrics create --name "Completed jobs" \
  --code completed_jobs --aggregation-type count_agg --dry-run
lago plans create --input @billing/lago-plan.json --dry-run
```

Review the resolved API URL, currency, base amount, included usage, overage price, and effective dates. `--dry-run` does not compare your request with existing Lago configuration. A plan charge needs the **actual metric ID** after metric creation; do not submit a placeholder. Ask the agent to show the complete diff and exact target before any live configuration write. See the [metric](/guide/lago-cli/commands/billable-metrics) and [plan](/guide/lago-cli/commands/plans) command references.

## 4. Prove the amount and retry behavior

The example repository includes a [reference fixture](https://github.com/anhtho-lago/growth-agent-billing-lab#verify-usage-in-isolated-self-hosted-lago). Its generator writes a Lago CLI scenario, an optional invoice-preview request, the original event for replay, and an expected-money file from the application's durable usage record. Run it **only** on an isolated self-hosted Lago instance:

```bash
PROOF_DIR="$(mktemp -d)"
PROOF_PREFIX="lab_$(date +%s)"
PYTHONPATH=src python3 -m growth_lab.lago_reference build \
  --output-dir "$PROOF_DIR/proof" --prefix "$PROOF_PREFIX"
lago fixtures run "$PROOF_DIR/proof/scenario.yaml" --mode test --dry-run
```

After `lago whoami` confirms the isolated target, run the fixture and compare current usage with the source-side calculation:

```bash
lago fixtures run "$PROOF_DIR/proof/scenario.yaml" --mode test
lago customers current-usage "${PROOF_PREFIX}_new_acme" \
  --external-subscription-id "${PROOF_PREFIX}_enrollment_001" \
  --output json > "$PROOF_DIR/usage.json"
PYTHONPATH=src python3 -m growth_lab.lago_reference verify-usage \
  --expected "$PROOF_DIR/proof/expected.json" \
  --usage "$PROOF_DIR/usage.json"
```

The expected usage is 75,000 credits and the expected overage charge is **\$1,250**; the \$500 base fee is separate. If the first read shows zero, wait for usage processing and read again rather than sending another event. Replay the original event with the same ID **and timestamp**, then verify that usage has not increased:

```bash
if lago api POST /events --data "@$PROOF_DIR/proof/event-request.json" \
  --output json > "$PROOF_DIR/replay.json" 2>&1; then
  echo "Unexpectedly accepted a duplicate event" >&2
  exit 1
fi
PYTHONPATH=src python3 -m growth_lab.lago_reference verify-replay \
  --replay "$PROOF_DIR/replay.json"
lago customers current-usage "${PROOF_PREFIX}_new_acme" \
  --external-subscription-id "${PROOF_PREFIX}_enrollment_001" \
  --output json > "$PROOF_DIR/usage-after-retry.json"
PYTHONPATH=src python3 -m growth_lab.lago_reference verify-usage \
  --expected "$PROOF_DIR/proof/expected.json" \
  --usage "$PROOF_DIR/usage-after-retry.json"
```

Lago returns HTTP 422 with `transaction_id: value_already_exist` for this duplicate in the tested standard self-hosted instance. The CLI exits nonzero; the replay verifier checks that exact reason, then the usage verifier checks that the amount stayed the same. A different error is a failed test.

<Info>[Invoice preview requires a Premium license](/guide/invoicing/previews), including on self-hosted Lago. On an isolated Self-Hosted Premium instance, use the generated `preview-request.json` and `verify` command to compare the full preview with the expected \$1,750 pretax amount. Standard self-hosted Lago can complete the current-usage and replay checks above.</Info>

```bash
# Self-Hosted Premium only, after the current-usage check passes.
lago invoices preview --input "@$PROOF_DIR/proof/preview-request.json" \
  --output json > "$PROOF_DIR/preview.json"
PYTHONPATH=src python3 -m growth_lab.lago_reference verify \
  --expected "$PROOF_DIR/proof/expected.json" \
  --preview "$PROOF_DIR/preview.json"
```

For your own product, trace one customer through subscription, source action, usage event, and current usage. When invoice preview is available, compare quantity, base charge, usage charge, credits, taxes, and total with an independent calculation. Do not treat a successful event response as proof of correct billing. The [integration testing guide](/guide/integration-testing) covers the broader lifecycle.

## If the result differs

| Symptom | First check |
| --- | --- |
| `lago` runs Docker Compose | Run `lago version`; remove a self-hosted shell alias shadowing the CLI. |
| Authentication or wrong organization | Run `lago doctor` and `lago whoami`; verify API host and key. |
| Event exists but usage is zero | Check the subscription's active period, metric code, event timestamp, and aggregation property. |
| Fixture says it requires a test profile | Add `--mode test` to `lago fixtures run`; confirm the exact isolated target with `lago whoami` first. The flag does not create a sandbox. |
| A replay increases usage | Compare both the original `transaction_id` and explicit `timestamp`. |
| Usage or preview differs from expected money | Check plan charge, billing period, customer overrides, taxes, credits, and whether the base fee was billed in advance. |

Use the [evaluation rubric](https://github.com/anhtho-lago/growth-agent-billing-lab/blob/main/evals/README.md) to compare agent runs. Record actual diffs, tests, and live checks; mark anything not run as **not tested**.
