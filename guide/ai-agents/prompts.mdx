---

Open your application repository in Claude Code, Codex, or another coding agent, then paste the prompt for the job you want done. Replace text in `[brackets]` with your own pricing or environment. You can explore and build local tests without a Lago account. For live work, [connect to the right organization](/guide/lago-cli/coding-agents#3-connect-to-the-right-lago-organization) first. Keep your API key in your terminal or secret manager, never in a prompt or source file.

If you installed the [Lago plugin](/guide/ai-agents/for-agents#pick-your-agent), ask the agent to use its **Lago implementation skill** with any prompt below. For a complete walkthrough, start with [Build Lago billing with a coding agent](/guide/lago-cli/coding-agents).

## Understand your app and pricing

### 1. Find the billing boundary

```text
Inspect this repository and map how customers pay today. Identify which
system sets prices, manages subscriptions, issues invoices, and collects
payments. Show the code and records behind each answer. Recommend which
responsibilities Lago should take, and flag any path that could bill a
customer twice. Do not edit code or contact a live billing system.
```

### 2. Find the billable action

```text
Our product charges for [customer action]. Find the application record that
proves this action happened. Show when it is created, its stable ID and
timestamp, the customer it belongs to, and cases where the action is
cancelled or retried. Propose the Lago usage event we should send and
explain anything the current data cannot prove. Do not edit code yet.
```

### 3. Turn a pricing brief into a bill

```text
Our pricing is [describe base fee, included units, usage rates, billing
period, and currency]. Calculate a bill for [example customer and usage].
Show each line item and the formula. Then map the rules to Lago metrics,
plan charges, and any credits. Identify decisions the brief leaves open,
including proration, taxes, and when charges become effective. Do not
create anything in Lago.
```

### 4. Compare pricing options

```text
We are considering [pricing option A] and [pricing option B]. Use these
three customer usage examples: [examples]. Calculate the bill under each
option, then explain the trade-offs for customers and implementation in
Lago. Recommend one option and list the exact questions we must answer
before configuring a plan. Do not change our app or Lago organization.
```

### 5. Choose customer and subscription IDs

```text
Find our existing customer, account, subscription, and workspace IDs.
Recommend stable external IDs for Lago customers and subscriptions. Trace
how a usage record reaches the paying customer, including account moves
and multiple workspaces. Show collisions or missing mappings and the code
that would need to change. Do not create Lago customers yet.
```

### 6. Plan a move from current billing

```text
We currently bill through [system]. Inspect the subscription, invoice,
payment, and usage paths in this repo. Propose a staged move of [customer
segment] to Lago. Define the cutover date, who owns each invoice before
and after it, how to avoid duplicate charges, how to reconcile the first
bill, and how to roll back. Flag any decision that needs finance approval.
Do not change production billing.
```

## Build and test in your repository

### 7. Add the smallest working integration

```text
Implement the billing plan we reviewed for [billable action]. Use a Lago
SDK or REST API from server-side code. Keep the API key in the existing
secret-management pattern. Add local tests for one complete example bill.
Preserve current billing paths unless we explicitly agreed to change them.
Show the diff and test results before contacting a live Lago organization.
```

### 8. Make usage retries safe

```text
Trace how [billable action] is recorded and retried. Make the Lago event's
transaction_id come from that durable app record, and reuse its original
timestamp on every retry. Check Lago's current idempotency guidance.
Test a timeout, a duplicate job, and a replay so one action produces one
billed unit. Show which failures still need an operator to intervene.
```

### 9. Implement a base fee with overage

```text
We charge [base amount] per [billing period], including [number] units,
then [overage rate] for each extra unit. Inspect our usage records and
implement the server-side Lago integration for this rule. Calculate bills
at zero usage, exactly the included amount, and above it without relying
on Lago's answer. Add local tests and show the proposed Lago plan as a
dry run before any live configuration change.
```

### 10. Meter AI usage

```text
We want to charge for [requests, tokens, or compute time]. Find where this
app receives the provider's final usage count. Propose one billable event
per completed operation, with a stable operation ID, original timestamp,
customer mapping, and the measured quantity. Explain how failed,
cancelled, streamed, and retried operations behave. Implement and test
the event path only after showing the event contract for review.
```

### 11. Model prepaid credits

```text
Our customers buy [credit amount] and spend credits on [usage]. Read
Lago's current wallet and prepaid-credit docs. Show when credits become
available, which charges consume them, what happens at zero balance, and
the difference between purchased and granted credits. Calculate a sample
balance and invoice. Propose configuration and code, but make no wallet
transactions or customer charges yet.
```

### 12. Handle subscription changes

```text
Find how this app starts, upgrades, downgrades, pauses, and cancels a
subscription. Map those actions to Lago's current subscription API and
documented billing timing. Show one timeline with expected charges for
each transition. Implement only the transition we agree to test first,
with local tests and no live customer changes.
```

### 13. Process Lago webhooks

```text
We need our app to react to [invoice or payment event]. Check Lago's
current webhook docs, then inspect our existing webhook handler pattern.
Implement signature verification if supported for our setup, durable
deduplication, safe retries, and a test for repeated delivery. Name the
source of truth for the resulting app state. Do not expose a new public
endpoint or change production settings until the diff is reviewed.
```

### 14. Build a billing test matrix

```text
Create focused local tests for our Lago integration using the agreed
pricing rules. Cover zero usage, the included boundary, overage, duplicate
events, a delayed event, a different customer, and a subscription change
if our app supports one. Calculate expected amounts independently from
Lago responses. Run the tests and show any case that cannot yet be proved.
```

## Connect and configure Lago

### 15. Get the right access

```text
Help me identify the access I need for this Lago integration. Ask whether
my team uses Lago Cloud US, Lago Cloud EU, or self-hosted Lago. Tell me
who should invite me or how to request a new Cloud organization, where
to find Developers > API keys after sign-in, and what API URL I need for
self-hosted Lago. Do not ask me to paste a key into chat. Do not access
or change an organization yet.
```

### 16. Set up the CLI

```text
Set up the Lago CLI in this development environment. Check the operating
system and whether lago is already installed. Give me a safe way to set
LAGO_API_KEY in my terminal or secret manager without printing it or
saving it in the repo. Ask for my Cloud region or self-hosted API URL.
Run lago version, initialize the CLI using the environment variable,
then run lago whoami and lago doctor. Show the connected host and
organization. Stop if they are not the target I named. Make no billing
data changes.
```

### 17. Check a self-hosted connection

```text
I have access to a self-hosted Lago instance at [web app URL]. Help me
identify the API service's base URL, without assuming it matches the web
app URL. Check CLI availability, connect using LAGO_API_KEY from my
environment, and run read-only connection checks. Report the host,
organization, and any failing service. Do not create test customers or
change plans on this instance.
```

### 18. Inspect the existing catalog

```text
The CLI is connected to [expected organization and host]. Read its
existing billable metrics and plans. Compare their codes, aggregation,
charges, currency, and billing intervals with [our pricing brief].
Show what can be reused and what conflicts. Treat this organization as
production: read only, and do not assume an empty list means a safe
place for test data.
```

### 19. Prepare a metric and plan dry run

```text
Using [approved pricing brief] and the current Lago catalog, prepare
the billable metric and plan we need. Check the latest CLI command
reference and API schema. Run CLI dry runs and show their output, the
target host, currency, base amount, included units, overage rate, and
effective dates. Identify the metric ID the plan will need after metric
creation. Stop before any live write.
```

### 20. Review a configuration change

```text
Compare our proposed Lago metric and plan with the actual configuration
in [expected organization]. Show a field-by-field change list, the
customers who could be affected, and one example bill before and after.
Check whether this change needs a new plan instead of editing an existing
one. Present the exact API or CLI requests for review. Do not execute them.
```

## Check a bill and investigate problems

### 21. Compare one customer's usage

```text
For [customer ID], [subscription ID], and [billing period], calculate
the expected quantity and charge from our application's own records and
pricing rules. Read Lago's current usage for that subscription and
compare quantities, amounts, and time boundaries. Show the source of
each number and every difference. Do not send more events to make the
totals match.
```

### 22. Test a duplicate in an isolated environment

```text
In our separate test organization or isolated self-hosted instance,
choose one test usage record. Send its Lago event, read current usage,
then retry with the same transaction_id and original timestamp. Wait for
processing before the second read. Show the two quantities and charges
and whether the retry changed them. Stop if this is a shared production
organization or the record belongs to a real customer.
```

### 23. Check an invoice preview

```text
If this organization has Lago Premium, preview the invoice for [test
customer and subscription]. Independently calculate the base charge,
usage, credits, tax assumptions, and expected total from our records.
Compare each invoice line with that calculation and explain differences.
If invoice preview is unavailable, say so and use current usage for the
checks it can support. Do not finalize or issue an invoice.
```

### 24. Diagnose zero usage

```text
Our app sent an event for [test record], but Lago current usage shows
zero. Trace the event's customer, subscription, metric code, properties,
timestamp, and response. Check whether the subscription is active and
allow for processing delay before reading again. Show the most likely
cause with evidence and the smallest safe fix. Do not resend the event
with a new transaction_id.
```

### 25. Explain a billing mismatch

```text
Our app calculates [expected amount] for [customer and period], while
Lago shows [observed amount]. Recalculate from source usage records.
Inspect the plan charge, included units, aggregation, billing period,
customer overrides, credits, taxes, and advance billing. Separate the
first proven difference from possible causes. Propose a fix and its
customer impact; do not alter an issued invoice or live plan.
```

### 26. Prepare the first live rollout

```text
We have passed local tests and checked one bill in [separate test
organization]. Prepare a rollout plan for [customer segment]. List the
configuration to promote, the first customers and billing periods to
compare, who will review the first invoices, and the signal to pause.
Show how existing billing is turned off for exactly those customers so
they cannot be charged twice. Do not perform the production cutover.
```
