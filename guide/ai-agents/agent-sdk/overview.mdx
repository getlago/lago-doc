title: "Overview"
description: "Bill LLM token usage directly from your application. Wrap your provider client, ship events to Lago, no middleware to maintain."
---

Pricing AI features requires per-token billing. Historically that meant building middleware to extract usage from every provider, normalize it across response shapes, batch events to a billing system, and survive outages. That work isn't your product.

The **Lago Agent SDK** removes that layer. You wrap your existing LLM client and keep calling it the same way: same arguments, same return shape, same exceptions. The SDK extracts normalized token usage from each response and streams events to Lago in the background.

It can also price calls for you. The SDK fetches live per-token prices, turns the priced token types on each call into a dollar cost, and lets you add a margin on top. Your LLM costs land in one place, and you decide what to resell them for.

Available in two flavors, both open source and versioned together:

- **Python**: [`lago-agent-sdk`](https://github.com/getlago/lago-agent-sdk-python) on PyPI. Python 3.10+.
- **JavaScript / TypeScript**: [`lago-agent-sdk`](https://github.com/getlago/lago-agent-sdk-js) on npm. Authored in TypeScript, ships compiled JS with `.d.ts`.

## How it works

```text
                  ┌────────────────┐
your code ──────▶ │ wrapped client │ ──────▶ provider (OpenAI / Bedrock / …)
                  └────────┬───────┘
                           │ (extract usage)
                           ▼
                  ┌────────────────┐
                  │  Lago events   │ ──────▶ api.getlago.com
                  └────────────────┘
```

- Wraps your existing LLM client in place. Your application code does not change.
- Extracts usage from each response into a normalized shape (`CanonicalUsage`, 11 numeric fields).
- Buffers events in memory and flushes them in batches to Lago's `/events/batch` endpoint.
- Survives provider and Lago outages with exponential backoff and a bounded buffer.
- Never blocks your LLM call on Lago. The measured p99 cost of an `emit()` is 23 µs.
- Never breaks your LLM call. Instrumentation errors are caught, logged, and optionally forwarded to your observability stack.

## Quickstart

<Steps>
  <Step title="Install the SDK">
    Install the core package plus the provider SDK you already use. Python ships provider support as extras, JavaScript as peer packages.

    <CodeGroup>
      ```bash pip
      pip install lago-agent-sdk

      # Add the provider you use:
      pip install 'lago-agent-sdk[openai]'      # adds openai
      pip install 'lago-agent-sdk[anthropic]'   # adds anthropic
      pip install 'lago-agent-sdk[bedrock]'     # adds boto3
      pip install 'lago-agent-sdk[gemini]'      # adds google-genai
      pip install 'lago-agent-sdk[mistral]'     # adds mistralai

      # Or several at once:
      pip install 'lago-agent-sdk[openai,anthropic]'
      ```

      ```bash npm
      npm install lago-agent-sdk

      # Plus the provider SDK(s) you use:
      npm install openai
      npm install @anthropic-ai/sdk
      npm install @aws-sdk/client-bedrock-runtime
      npm install @google/genai
      npm install @mistralai/mistralai
      ```
    </CodeGroup>
  </Step>

  <Step title="Initialize and wrap your LLM client">
    Pass your Lago API key and a default `external_subscription_id`, then wrap your provider client. The returned object is a drop-in replacement, and `wrap()` is idempotent: calling it twice on the same client is a no-op.

    <CodeGroup>
      ```python Python
      from openai import OpenAI
      from lago_agent_sdk import LagoSDK

      sdk = LagoSDK(
          api_key="<YOUR_LAGO_API_KEY>",
          default_subscription_id="sub_acme",
      )
      client = sdk.wrap(OpenAI(api_key="<YOUR_OPENAI_API_KEY>"))
      ```

      ```typescript TypeScript
      import OpenAI from "openai";
      import { LagoSDK } from "lago-agent-sdk";

      const sdk = new LagoSDK({
        apiKey: process.env.LAGO_API_KEY!,
        defaultSubscriptionId: "sub_acme",
      });
      const client = sdk.wrap(new OpenAI({ apiKey: process.env.OPENAI_API_KEY! }));
      ```
    </CodeGroup>

    <Tip>
      On the EU region or a self-hosted instance, set `api_url` / `apiUrl`. The default is `https://api.getlago.com/api/v1`.
    </Tip>
  </Step>

  <Step title="Make LLM calls normally">
    The wrapped client preserves the original signature, return shape, and exceptions. No call-site changes required.

    <CodeGroup>
      ```python Python
      resp = client.chat.completions.create(
          model="gpt-4o-mini",
          messages=[{"role": "user", "content": "Hello"}],
          max_completion_tokens=200,
      )
      ```

      ```typescript TypeScript
      await client.chat.completions.create({
        model: "gpt-4o-mini",
        messages: [{ role: "user", content: "Hello" }],
        max_completion_tokens: 200,
      });
      ```
    </CodeGroup>

    <Tip>
      Streaming works the same way. The SDK wraps the iterator, reads usage from the terminal chunk, and emits one set of events per completed response. See your provider's page for the exact streaming surface.
    </Tip>
  </Step>

  <Step title="Flush events on shutdown">
    Events flush automatically: every second, or as soon as 100 events are buffered. Call `flush()` explicitly at process exit (FastAPI shutdown hook, Express server close, AWS Lambda extension) so in-flight events are not lost.

    <CodeGroup>
      ```python Python
      sdk.flush()          # returns True when the buffer drained
      ```

      ```typescript TypeScript
      await sdk.flush();   // resolves to true when the buffer drained
      ```
    </CodeGroup>

    <Note>
      A clean interpreter exit already triggers a 2-second flush. Python registers an `atexit` hook, JavaScript a `beforeExit` handler. An explicit `flush()` is still the right call in a request-scoped or serverless runtime.
    </Note>
  </Step>

  <Step title="Register billable metrics in Lago">
    Before events count toward charges, register matching billable metrics in your Lago tenant. The SDK ships with default metric codes (see [Captured token dimensions](#captured-token-dimensions)). Register each one you plan to bill on as a `sum_agg` metric.

    Follow [Create a billable metric](/api-reference/billable-metrics/create) to set them up, then attach charges to them in your plan. For a full worked example, see the [per-token pricing template](/templates/per-token/openai).
  </Step>
</Steps>

## Bill in tokens or in dollars

The SDK can bill two ways. By default it sends **token counts**, and you turn those into money with your Lago plans. Switch to **price mode** and the SDK sends the **dollar cost** of each call instead. It looks up the per-token price of the model, multiplies by the tokens used, applies your markup, and emits cost events.

**Where prices come from.** OpenRouter for native OpenAI, Anthropic, Mistral, and Gemini clients. The AWS Bedrock public bulk price list for Bedrock, parsed per region. Cloudflare's own model catalog for Workers AI, which is the one source that needs credentials. No price file for you to maintain. Prices refresh in the background on the queue thread, so your LLM call is never slowed down waiting on a price.

A gateway that meters its own real cost per call beats any price the SDK can compute. Pass that number through with `usd_cost` / `usdCost` and the lookup is skipped entirely. See [Cloudflare AI Gateway](/guide/ai-agents/agent-sdk/cloudflare#backfill-path).

**Prices are keyed off the model that answered, not the one you asked for.** Providers resolve short aliases to dated snapshots server-side (`claude-sonnet-4-5` becomes `claude-sonnet-4-5-20250929`, Mistral's `-latest` and Gemini's aliases hot-swap the same way), and OpenRouter lists the snapshot rather than the alias. The OpenAI, Anthropic, and Gemini adapters read the model off the response and fall back to the requested id only when the response is silent about it. Mistral `-latest` aliases are resolved against Mistral's own `/v1/models`.

**Add your margin.** Set a `markup` to resell LLM access at a profit. `1.2` means the customer pays your cost plus 20%.

<CodeGroup>
  ```python Python
  from lago_agent_sdk import LagoConfig, LagoSDK

  sdk = LagoSDK(
      api_key="...",
      config=LagoConfig(
          api_key="...",
          default_subscription_id="sub_acme",
          pricing_mode="price",   # "tokens" (default) | "price"
          markup=1.2,             # optional. 1.2 = +20%
      ),
  )
  client = sdk.wrap(openai_client)
  ```

  ```typescript TypeScript
  import { LagoSDK } from "lago-agent-sdk";

  const sdk = new LagoSDK({
    apiKey: "...",
    defaultSubscriptionId: "sub_acme",
    config: {
      pricingMode: "price", // "tokens" (default) | "price"
      markup: 1.2,          // optional. 1.2 = +20%
    },
  });
  const client = sdk.wrap(openaiClient);
  ```
</CodeGroup>

You can also flip a single call to price mode and set a one-off markup. Python: `extra_lago={"mode": "price", "markup": 1.5}`. TypeScript: `lago: { mode: "price", markup: 1.5 }`. For Bedrock, attach it to the command as `__lago`.

<Note>
  **Lago setup for price mode.** Register a `sum` billable metric `llm_cost` on `field_name: "unit"` and attach a **dynamic** charge to it. Lago sums each event's `precise_total_amount_cents` into a single fee, and `unit` is the displayed usage quantity.

  Group the charge by `["model", "token_type"]` so one metric breaks the cost down by both dimensions.
</Note>

**What price mode emits.** One `llm_cost` event **per priced token type**, not one per call. Each event carries `precise_total_amount_cents` at the top level, plus `token_type`, `unit` (tokens of that type), `value` (billed cost after markup), `base_cost` (before markup), `unit_price`, `markup`, `price_source`, `model`, `provider`, and `api` in `properties`.

The exception is a cost the SDK did not compute. When a gateway reports its own metered cost per call and you pass it through, there is no per-field split to report, so that path emits a **single** event with no `token_type` rather than inventing a proportional breakdown. See [Cloudflare AI Gateway](/guide/ai-agents/agent-sdk/cloudflare#backfill-path).

<Warning>
  **Price mode prices five fields.** `input`, `output`, `cache_read`, `cache_write`, and `reasoning`. Tool calls, audio, image, and the 5-minute and 1-hour cache-write splits carry no unit price, so they produce no cost event. A call whose only counts are unpriced yields a total of `0` rather than disappearing.

  If you bill on those dimensions, meter them in token mode instead of, or alongside, price mode.
</Warning>

<Tip>
  **Subset overlaps are handled for you.** Where a provider's `input` already contains the cached tokens (OpenAI and Gemini), the cached portion is moved out of `input` and billed at the cache-read rate, so it is charged once at the right price. Where `output` already contains reasoning tokens (OpenAI), the separate reasoning line is dropped rather than billed twice. This is the double-counting trap from [Captured token dimensions](#captured-token-dimensions), except price mode resolves it instead of leaving it to your plan.
</Tip>

<Warning>
  **Never under-bill.** If a price is not available (the price table has not warmed up on the very first call, or the model is missing from the source), the SDK falls back to emitting normal token-count events and fires `on_error` / `onError` so you can see it. It never silently drops the usage.
</Warning>

<Warning>
  **Bedrock pricing gap.** AWS's public bulk data lists many models (Titan, Llama, Mistral, Cohere, older Claude) but, at time of writing, not the current Claude 3.5/3.7/4 models. Bedrock calls for models absent from AWS's data fall back to token events. Native Anthropic clients are priced via OpenRouter and unaffected.
</Warning>

## Captured token dimensions

The SDK normalizes every provider response into a `CanonicalUsage` object with 11 numeric fields, and emits one event per non-zero field. The default metric codes match Lago's conventions. Override them in the config if your tenant already uses different names.

| Canonical field  | Default Lago metric code    | Bedrock                  | Anthropic | Mistral            | OpenAI            | Gemini              |
|------------------|-----------------------------|--------------------------|-----------|--------------------|-------------------|---------------------|
| `input`          | `llm_input_tokens`          | ✓                        | ✓         | ✓                  | ✓                 | ✓                   |
| `output`         | `llm_output_tokens`         | ✓                        | ✓         | ✓                  | ✓                 | ✓                   |
| `cache_read`     | `llm_cached_input_tokens`   | ✓ (Anthropic)            | ✓         | ✓ (on cache hit)   | ✓ (auto-cache)    | ✓ (CachedContent)   |
| `cache_write`    | `llm_cache_creation_tokens` | ✓ (Anthropic)            | ✓         | ✗                  | ✗                 | ✗                   |
| `cache_write_5m` | `llm_cache_write_5m_tokens` | ✓ (Anthropic InvokeModel)| ✓         | ✗                  | ✗                 | ✗                   |
| `cache_write_1h` | `llm_cache_write_1h_tokens` | ✓ (Anthropic InvokeModel)| ✓         | ✗                  | ✗                 | ✗                   |
| `reasoning`      | `llm_reasoning_tokens`      | folded into `output`     | folded into `output` | folded into `output` | ✓ (o-series)  | ✓ (Gemini 2.5)      |
| `tool_calls`     | `llm_tool_calls`            | ✓                        | ✓         | ✓                  | ✓                 | ✓                   |
| `image_input`    | `llm_image_input_tokens`    | ✗                        | ✗         | ✗                  | ✗                 | ✓                   |
| `audio_input`    | `llm_audio_input_tokens`    | ✗                        | ✗         | ✗                  | ✓ (audio models)  | ✓                   |
| `audio_output`   | `llm_audio_output_tokens`   | ✗                        | ✗         | ✗                  | ✓ (audio models)  | ✓                   |

<Warning>
  **Do not sum subset fields into your total.** `cache_read`, `audio_input`, and `image_input` are breakdowns *inside* `input`, not additions to it. OpenAI reports `cached_tokens` under `prompt_tokens_details` within `prompt_tokens`, and Gemini's `promptTokenCount` already includes cached content. A billable metric that sums `llm_input_tokens + llm_cached_input_tokens` double-counts.

  Bill on `llm_input_tokens` as the total. Use the breakdown fields for cost attribution or discounted-rate tiers (cached input at a lower rate), subtracting them from `input` rather than adding.
</Warning>

<Warning>
  **`reasoning` is a subset on OpenAI, additive on Gemini.** OpenAI's `reasoning_tokens` are already counted inside `completion_tokens`. Gemini's `thoughtsTokenCount` is additive to `candidatesTokenCount`, so your total Google bill is output plus reasoning. Model the charge accordingly.
</Warning>

Every event also carries `model`, `provider`, and `api` in its `properties`, so you can build filter-based charges without passing anything extra. `api` is one of `chat_completions`, `responses`, `native`, `bedrock_converse`, `bedrock_invoke`, or `cloudflare_gateway`.

`provider` is derived rather than assumed, since one client can reach several providers. A Bedrock client produces events tagged `anthropic`, `amazon`, `meta`, `mistral`, and so on from the model id. An OpenAI-shaped client pointed at a Cloudflare gateway produces `workers-ai` when the resolved model starts with `@cf/`.

## Multi-tenant: pick a subscription per call

Lago needs to know which customer to bill for each LLM call. The SDK resolves the `external_subscription_id` in this priority order:

1. **Per-call override**: highest precedence, attached to the individual request.
2. **Context-bound**: set once per request handler. Propagates safely across async boundaries via `contextvars` (Python) and `AsyncLocalStorage` (Node).
3. **Default at init**: fallback if nothing else is set.

<CodeGroup>
  ```python Python
  # 1. Per-call override (highest precedence)
  client.chat.completions.create(
      model="gpt-4o-mini",
      messages=[{"role": "user", "content": "Hello"}],
      extra_lago={
          "subscription": "sub_acme",
          "dimensions": {"feature": "summarize", "user_id": "u_42"},
      },
  )

  # 2. Context-bound. Propagates across asyncio tasks via contextvars.
  token = sdk.set_subscription("sub_acme")
  # all calls in this thread/asyncio task → sub_acme
  sdk.reset_subscription(token)

  # 3. Default at init (fallback)
  sdk = LagoSDK(api_key="...", default_subscription_id="sub_default")

  # Also available: bind at wrap time for a whole client
  client = sdk.wrap(openai_client, subscription="sub_acme", dimensions={"env": "prod"})
  ```

  ```typescript TypeScript
  // 1. Per-call override. Pass `lago` in the args object.
  await client.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [{ role: "user", content: "Hello" }],
    lago: {
      subscription: "sub_acme",
      dimensions: { feature: "summarize", user_id: "u_42" },
    },
  } as any);

  // 2. Context-bound. AsyncLocalStorage, safe across awaits.
  await sdk.withSubscription("sub_acme", async () => {
    await client.chat.completions.create(/* … */);
  });
  // or at the top of a request handler:
  sdk.setSubscription("sub_acme");

  // 3. Default at init (fallback)
  new LagoSDK({ apiKey: "...", defaultSubscriptionId: "sub_default" });

  // Also available: bind at wrap time for a whole client
  const client = sdk.wrap(openaiClient, { subscription: "sub_acme", dimensions: { env: "prod" } });
  ```
</CodeGroup>

<Tip>
  Any `dimensions` you pass go through to the event as `properties`. Useful for filter-based charges on model, feature, or region. See [Charges with filters](/guide/plans/charges/charges-with-filters).
</Tip>

<Warning>
  If subscription resolution returns nothing (no per-call override, no context, no default), the event is dropped and an error is logged. Make sure at least one of the three levels is set before your first call.
</Warning>

## Under the hood

Two goals conflict on a single thread. Your code has to return as fast as possible, and every billable event has to eventually reach Lago. A synchronous Lago call would add hundreds of milliseconds to every LLM call. A fire-and-forget call would lose events.

The SDK splits the two across a **foreground path** and a **background worker** that share a thread-safe in-memory queue.

```text
┌────────────────────────────────────────────────────────────────┐
│  Your application                                              │
│                                                                │
│   client.chat.completions.create(...)                          │
│              │                                                 │
│              ▼   (instrumented by sdk.wrap)                    │
│   ┌─────────────────────────────────────────────────┐          │
│   │  FOREGROUND — your own thread                   │          │
│   │   1. Adapter extracts usage from the response   │          │
│   │   2. Build CanonicalUsage (11 numeric fields)   │          │
│   │   3. Resolve subscription (contextvar)          │          │
│   │   4. queue.push(event) per non-zero field       │          │
│   │   5. Return    ← total ~5 µs                    │          │
│   └─────────────────────────────────────────────────┘          │
│              │                                                 │
│              ▼                                                 │
│   ┌─────────────────────────────────────────┐                  │
│   │  In-memory buffer                       │                  │
│   │  FIFO deque, cap 10,000 events          │                  │
│   │  [E1] [E2] [E3] [E4] ... [En]           │                  │
│   └─────────────────────────────────────────┘                  │
│              ▲                                                 │
│              │  pulled in batches of up to 100                 │
│   ┌─────────────────────────────────────────────────┐          │
│   │  BACKGROUND — daemon thread                     │          │
│   │   loop:                                         │          │
│   │     • wait for wake signal OR 1s timer          │          │
│   │     • take a batch of up to 100 events          │          │
│   │     • POST batch to Lago (~550 ms roundtrip)    │          │
│   │     • on success: drop the batch, reset backoff │          │
│   │     • on failure: re-prepend batch + back off   │          │
│   └─────────────────────────────────────────────────┘          │
└──────────────┼─────────────────────────────────────────────────┘
               │  HTTPS
               ▼
   ┌────────────────────────────────────────────────┐
   │  POST /api/v1/events/batch                     │
   │  (Lago accepts max 100 events per request)     │
   └────────────────────────────────────────────────┘
```

The slow HTTP POST never touches your request path.

<AccordionGroup>
  <Accordion title="The foreground path, step by step">
    Every line that runs synchronously on your thread when an LLM call returns:

    | Step | Operation | Cost |
    |------|-----------|------|
    | 1 | Adapter extracts usage from the provider response | under 1 µs |
    | 2 | Build `CanonicalUsage` (11 numeric fields) | under 1 µs |
    | 3 | Resolve subscription (contextvar lookup, fallback to default) | ~100 ns |
    | 4 | For each non-zero field, build an event dict (uuid4, timestamp, properties) | ~5 µs |
    | 5 | `queue.push(event)`: acquire lock, append to deque, release | under 1 µs |

    A 10,000-iteration micro-benchmark of `sdk.emit()`:

    | Statistic | Latency per `emit()` |
    |-----------|----------------------|
    | mean | 5.7 µs |
    | p50 | 4.7 µs |
    | p95 | 8.9 µs |
    | p99 | 23.4 µs |
    | p99.9 | 38.1 µs |
    | max observed | 62.5 µs |

    A real LLM call takes 500 to 2,000 ms. At p99 the SDK adds roughly 23 µs, about four orders of magnitude below the call it instruments.
  </Accordion>

  <Accordion title="The buffer">
    ```text
                   Producer side
                   sdk.emit()
                        │  append newest at the right end
                        ▼
    ┌──────────────────────────────────────────────────────┐
    │  FIFO deque    (max_buffer_size = 10,000 events)     │
    │   oldest →  [E1][E2][E3][E4][E5] ... [En]  ← newest  │
    └──────────────────────────────────────────────────────┘
        │                                       ▲
        │ take up to 100                        │  if full on a new
        │ from the oldest end                   │  push: drop oldest
        ▼                                       │
    ┌──────────────────────┐              ┌─────┴────────┐
    │  Background worker   │              │  DROPPED     │
    │  POSTs to Lago       │              │ oldest event │
    └──────────────────────┘              └──────────────┘
    ```

    - **FIFO.** Events drain in the order they were emitted.
    - **Bounded.** Hard cap at `max_buffer_size`, default 10,000.
    - **Sliding window on overflow.** Newest events evict oldest, with a warning per drop.
    - **Thread-safe.** A single lock around mutations.
    - **Memory cost.** Roughly 500 bytes per event in JSON form, so about 5 MB at the default cap.

    Dropping the oldest rather than the newest is deliberate. For billing reconciliation, recent events reflect what the customer is doing right now. Older events are more likely to have been aggregated or recovered already.
  </Accordion>

  <Accordion title="The background worker">
    A daemon thread started at SDK construction, running this loop:

    ```text
    while not stopping:
        wait_for(wake_signal, timeout=flush_interval)
        refresh pricing tables if stale     # off the hot path

        while buffer_not_empty():
            batch = take_up_to_100_events()
            if in_backoff: sleep(backoff_seconds)
            try:
                POST batch to /events/batch
                backoff_seconds = 0             # reset on success
            except (network error, 5xx, 4xx, timeout):
                put_batch_back_at_front_of_buffer()
                backoff_seconds = min(backoff * 2 or 1, max_retry_seconds)
                break
    ```

    Three things wake it:

    1. **`push()` reaching `max_batch_size`** (100 events). Bursts drain immediately, no waiting on the timer.
    2. **Timer expiry** every `flush_interval` (1 s default). Trickle traffic drains within a second.
    3. **`flush()` or `shutdown()`**, which force an immediate drain pass.

    Price-table refreshes also run on this thread, which is why price mode never adds latency to your call.
  </Accordion>

  <Accordion title="The HTTP batch">
    Each batch is one POST:

    ```http
    POST https://api.getlago.com/api/v1/events/batch
    Authorization: Bearer {LAGO_API_KEY}
    Content-Type: application/json

    {
      "events": [
        {
          "transaction_id": "uuid-v4",
          "external_subscription_id": "sub_acme",
          "code": "llm_input_tokens",
          "timestamp": 1716912345,
          "properties": {
            "value": "100",
            "model": "claude-haiku-4-5",
            "provider": "anthropic",
            "api": "native"
          }
        }
      ]
    }
    ```

    Lago's endpoint accepts a maximum of **100 events per request**, which is why `max_batch_size` defaults to 100. Measured roundtrip against `api.getlago.com` is around 550 ms per POST, dominated by server-side parse, validate, and persist rather than by payload size.
  </Accordion>
</AccordionGroup>

## Reliability

The design promise: **your LLM call never breaks because of the SDK.** Anything that goes wrong inside instrumentation is caught, logged, and either retried or absorbed. Your code receives the normal LLM response either way.

| Failure | SDK response | Events lost |
|---------|--------------|-------------|
| Adapter throws (provider drift, malformed response) | Catch, log a warning, call `on_error(exc, "emit")` | 1 event |
| Network blip on a single request | Re-prepend the batch, exponential backoff | 0 |
| Lago 5xx (transient) | Same as a network blip | 0 |
| Lago 4xx (invalid metric code, duplicate `transaction_id`) | Treated as permanent. The batch is retried one event at a time so a single bad event cannot block the rest, then dropped with a warning | The individually-rejected events only |
| Lago unreachable 10 min at 10 events/sec | Buffer holds roughly 17 minutes at the default cap | 0 |
| Lago unreachable 1 hour at 50 events/sec | Buffer fills, overflow drops oldest | Yes, oldest sacrificed |
| `flush()` called | Block until the buffer empties or the timeout expires | 0 |
| `shutdown()` called | Flush, stop the worker, join the thread, final drain | 0 within the timeout |
| Clean process exit | `atexit` / `beforeExit` runs a 2-second shutdown | 0 within 2 s |
| `SIGKILL` or OOM kill | No hooks run | Yes, buffered events lost |
| Fork (Gunicorn, uWSGI prefork) | `os.register_at_fork` recreates a fresh queue and lock in the child | 0. Parent and child each own a queue |
| `wrap()` called twice on one client | Idempotent, second call is a no-op | 0 |
| Async context switch | `contextvars` / `AsyncLocalStorage` propagate the subscription | 0. Concurrent requests do not cross-bleed |

<AccordionGroup>
  <Accordion title="Retry and exponential backoff">
    When a POST fails, the worker:

    Transient failures (5xx, timeout, connection error) are retried:

    1. **Re-prepends the failed batch** at the front of the buffer, preserving event order.
    2. **Doubles the backoff**: 1 s, 2 s, 4 s, 8 s, 16 s, 32 s, then capped at `max_retry_seconds` (60 s default).
    3. **Waits out the backoff** before the next attempt. No POSTs go out during backoff, but `push()` keeps accepting new events.
    4. **Resets the backoff to zero** on the first successful POST.

    ```text
    time   event                      backoff after
    ─────  ─────────────────────      ─────────────
    t=0    POST #1 fails              1s
    t=1    POST #2 fails              2s
    t=3    POST #3 fails              4s
    t=7    POST #4 fails              8s
    t=15   POST #5 fails              16s
    t=31   POST #6 fails              32s
    t=63   POST #7 fails              60s   (capped)
    …      stays at 60s until success
    t=N    POST succeeds              0s    (reset)
    ```

    If Lago stays down long enough, the buffer fills and overflow starts dropping the oldest events. Everything before that point is delivered.

    **Permanent failures are not retried.** A Lago 4xx will never succeed on a replay of the same batch, so retrying it would park a doomed batch at the front of the FIFO and block every valid event queued behind it for the full backoff ceiling, over and over. Instead the batch is re-sent one event at a time: an event that 4xxs alone is logged and dropped, one that succeeds is done, and one that hits a transient error while isolated goes back into the normal retry path. `on_error` fires once for the batch rather than once per event.

    The most common cause of a 4xx here is a duplicate `transaction_id`, which is exactly what a re-run of a backfill produces. See the [Cloudflare page](/guide/ai-agents/agent-sdk/cloudflare#two-new-emit-arguments) on scoping idempotency keys.
  </Accordion>

  <Accordion title="Buffer overflow">
    `max_buffer_size` is a hard memory ceiling. When a `push()` arrives and the buffer is already at the cap, the oldest event is discarded to make room and a warning is logged:

    ```python
    def push(self, event):
        with self._lock:
            if len(self._buffer) >= self._max_buffer_size:
                self._buffer.popleft()    # drop oldest
                logger.warning("lago queue overflow at %d events; dropping oldest", ...)
            self._buffer.append(event)
    ```

    Verified: pushing 50,000 events into a stuck queue with the default cap retains exactly 10,000 and logs a warning per drop. Raise `max_buffer_size` if you want a longer outage window and can afford the memory (roughly 500 bytes per event).
  </Accordion>

  <Accordion title="Shutdown lifecycle">
    `shutdown(timeout=5)` runs four steps in order:

    ```text
    1. flush(timeout)
         wake the worker, poll every 10 ms until the buffer is empty
         or the timeout expires (returns False on timeout)
    2. set the stopping flag
    3. wake the worker once more so it observes the flag
    4. thread.join(timeout)
         the worker exits its main loop, then runs ONE LAST drain:
         if the buffer is non-empty, send a final batch
    ```

    The last-chance drain at the bottom of the worker loop is the safety net. It catches events pushed between `flush()` returning and the stopping flag being set. `join(timeout)` guarantees shutdown never hangs, even if the worker is stuck mid-request.

    That final drain is itself bounded by a wall-clock budget, so an exiting daemon thread cannot spin forever against a network that is down. Anything still buffered when the budget runs out is logged as lost, explicitly, rather than dropped in silence.

    You rarely need to call this yourself: a clean interpreter exit already runs `shutdown(2.0)` through `atexit` (Python) or `beforeExit` (Node). A 2-second budget covers roughly 360 events of drain at the default settings.
  </Accordion>
</AccordionGroup>

## Throughput and operating envelope

The SDK's foreground cost is negligible. The ceiling is downstream: a single process drains at the rate of sequential HTTP POSTs multiplied by Lago's 100-event batch cap, which measures at roughly **180 events/sec**.

A sustained-load test at 500 emit/sec for 60 seconds against production Lago, with `max_buffer_size` raised to 200,000 and `flush_interval_seconds` lowered to 0.1:

| Quantity | Value |
|----------|-------|
| Total events generated | 60,000 |
| Events delivered to Lago | **60,000 (100%)** |
| Events dropped on overflow | 0 |
| Flush completed cleanly | Yes |
| HTTP POSTs total | 600 |
| Average events per POST | 100.0, every batch full |
| Steady-state drain rate | 178 events/sec |
| Buffer peak | 49,300, under the 200k cap |
| Producer duration | 60 s |
| Drain duration after the producer stopped | 284 s |

The buffer absorbed the difference between the 500 events/sec producer and the 180 events/sec drain, then `flush(timeout=600)` drained it to empty and returned `True`. Zero loss.

What that means for a single process on default configuration:

| Sustained emit rate | Outcome |
|---------------------|---------|
| ≤ 90 emit/sec | Buffer stays small. Every event delivered. |
| 90 to ~180 emit/sec | Buffer accumulates slowly. Drains or overflows depending on burst pattern. |
| > ~180 emit/sec sustained | Buffer fills, oldest events drop on overflow. |

<Note>
  One emit typically produces two or more events (input plus output tokens, more with caching), which is why the emit-rate envelope sits below the event-level drain rate.
</Note>

To go above the envelope:

- **Scale horizontally.** Each process runs its own queue and its own worker, so N processes drain at N × 180 events/sec. This is the recommended path today and it is what a normal multi-worker web server already gives you.
- **Raise `max_buffer_size`** to widen the outage and burst window. Memory is the only cost, roughly 500 bytes per event.
- **Use price mode** when the per-token event volume is the problem. Price mode emits **one** event per call instead of one per non-zero field, cutting event volume by a factor of two to five depending on caching.

## Error handling

<Info>
  The SDK **never breaks your LLM call**. If instrumentation fails (adapter bug, Lago unreachable, network error), the SDK catches the error, logs a warning, and your call returns normally.
</Info>

Because failures are silent by design, wire the `on_error` / `onError` hook on day one:

<CodeGroup>
  ```python Python
  import sentry_sdk
  from lago_agent_sdk import LagoConfig, LagoSDK

  def on_error(exc: Exception, where: str) -> None:
      sentry_sdk.capture_exception(exc, tags={"sdk_phase": where})

  sdk = LagoSDK(
      api_key="...",
      config=LagoConfig(api_key="...", on_error=on_error),
  )
  ```

  ```typescript TypeScript
  import * as Sentry from "@sentry/node";
  import { LagoSDK } from "lago-agent-sdk";

  new LagoSDK({
    apiKey: "...",
    config: {
      onError: (err, where) =>
        Sentry.captureException(err, { tags: { sdk_phase: where } }),
    },
  });
  ```
</CodeGroup>

The `where` argument tells you which phase failed: `emit`, `pricing`, or `send_batch`.

### Exception hierarchy

Both SDKs export the same error classes for callers that want to handle SDK errors explicitly:

- `LagoSDKError`: base class for every SDK-raised error.
- `LagoApiError`: non-2xx response from Lago. Carries `status` and `body`.
- `LagoConfigError`: invalid configuration at init time.
- `UnknownClientError`: `wrap()` was called on a client the SDK does not recognize. Subclasses `LagoConfigError`.
- `PricingUnavailableError`: price mode could not resolve a price. Surfaced through `on_error`, never raised at the call site.

## Verify the integration

<Steps>
  <Step title="Make a wrapped LLM call">

  <Step title="Check the event in Lago">

  <Step title="Confirm usage on the customer">

  </Step>
  <Step title="If nothing arrives">
