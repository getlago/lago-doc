A [billable metric](/v2/api-reference/billable-metrics/object) defines how Lago turns usage events into a quantity, such as a count of API calls or a sum of gigabytes. It measures usage but sets no price: a [metered product](/v2/guide/product-catalog/metered-products) uses the metric, and its [rate card](/v2/guide/rate-cards/overview) prices the quantity.

## How it fits together

| Object | Answers |
| --- | --- |
| Billable metric | How much was used? |
| Metered product | What do you sell? Set `billable_metric_code` on the product. |
| Product filter | Which slice of that usage? Built on the metric's `filters`. |
| Rate card and rate | What does it cost? |
| Contract | Who pays? Events carry `external_contract_id`. |

In the running example, the `api_calls` metric counts API calls. The metered product `api_calls_product` uses it, and the `api_calls_usd` rate card prices it at $0.01 per call. 2,000 calls give $20.00. The fixed $100 `monthly_service` product needs no metric.

## Metric fields

| Field | Example | Purpose |
| --- | --- | --- |
| `name` | `API calls` | Readable name. |
| `code` | `api_calls` | The code your events send so Lago can match them to the metric. |
| `description` | `Number of API calls` | Optional context for your team. |
| `aggregation_type` | `count_agg` | How events are aggregated: `count_agg`, `sum_agg`, `max_agg`, `unique_count_agg`, `weighted_sum_agg` or `latest_agg`. See [Aggregation types](/v2/guide/billable-metrics/aggregation-types/overview). |
| `field_name` | `gb` | The event property to aggregate. Required for every type except `count_agg`. |
| `expression` | `event.properties.gb * event.properties.replicas` | Optional computed value per event. See [SQL expressions](/v2/guide/billable-metrics/sql-expressions). |
| `weighted_interval` | `seconds` | Required for `weighted_sum_agg`. |
| `recurring` | `false` | Whether values carry over between billing periods. See [Recurring vs metered](/v2/guide/billable-metrics/recurring-vs-metered). |
| `rounding_function`, `rounding_precision` | `round`, `2` | Optional rounding of the aggregated value. See [Rounding](/v2/guide/billable-metrics/rounding). |
| `filters` | `[{ "key": "region", "values": ["us", "eu"] }]` | Dimensions you can slice and price separately. See [Filters and dimensions](/v2/guide/billable-metrics/filters). |

## Create the API calls metric

Use COUNT (`count_agg`) when each event is one API call. `field_name` is not needed.

<Tabs>
  <Tab title="Dashboard">
    1. Access the **Billable metrics** section in the side menu.
    2. Create a new billable metric.
    3. Enter its `name`, a `code` your events will send, and an optional `description`.
    4. Select the aggregation type that defines how consumption is measured.
    5. Define the property to aggregate, except for Count.
    6. Define `filters` if you price several dimensions of the same usage.
    7. Choose whether the metric is recurring (kept period over period) or metered (reset to 0 each period).
    8. Save the billable metric.
  </Tab>
  <Tab title="API">
    <CodeGroup>
    ```bash API calls (COUNT)
    LAGO_URL="https://api.getlago.com"
    API_KEY="__YOUR_API_KEY__"

    curl --location --request POST "$LAGO_URL/api/v2/billable_metrics" \
      --header "Authorization: Bearer $API_KEY" \
      --header 'Content-Type: application/json' \
      --data-raw '{
        "billable_metric": {
          "name": "API calls",
          "code": "api_calls",
          "description": "Number of API calls",
          "aggregation_type": "count_agg",
          "recurring": false
        }
      }'
    ```

    ```bash Storage (SUM with a filter)
    LAGO_URL="https://api.getlago.com"
    API_KEY="__YOUR_API_KEY__"

    curl --location --request POST "$LAGO_URL/api/v2/billable_metrics" \
      --header "Authorization: Bearer $API_KEY" \
      --header 'Content-Type: application/json' \
      --data-raw '{
        "billable_metric": {
          "name": "Storage",
          "code": "storage",
          "description": "Number of GB used",
          "aggregation_type": "sum_agg",
          "field_name": "gb",
          "recurring": false,
          "filters": [
            {
              "key": "provider",
              "values": ["aws", "google", "azure"]
            }
          ]
        }
      }'
    ```

    ```bash Seats (COUNT UNIQUE, recurring)
    LAGO_URL="https://api.getlago.com"
    API_KEY="__YOUR_API_KEY__"

    curl --location --request POST "$LAGO_URL/api/v2/billable_metrics" \
      --header "Authorization: Bearer $API_KEY" \
      --header 'Content-Type: application/json' \
      --data-raw '{
        "billable_metric": {
          "name": "Seats",
          "code": "seats",
          "description": "Active seats added",
          "aggregation_type": "unique_count_agg",
          "field_name": "seat_id",
          "recurring": true
        }
      }'
    ```

    ```bash CPUs (MAX)
    LAGO_URL="https://api.getlago.com"
    API_KEY="__YOUR_API_KEY__"

    curl --location --request POST "$LAGO_URL/api/v2/billable_metrics" \

          "name": "CPU",
          "code": "cpu",
          "description": "Maximum number of CPUs used",
    ```

## Verify the metric

Retrieve the metric and confirm that `code`, `aggregation_type` and `recurring` match. Add `expands[]=filters` to see its filters.

```bash Retrieve api_calls
LAGO_URL="https://api.getlago.com"
API_KEY="__YOUR_API_KEY__"

curl --location --globoff --request GET "$LAGO_URL/api/v2/billable_metrics/api_calls?expands[]=filters" \
  --header "Authorization: Bearer $API_KEY"
```

Creating the metric does not create a product, a contract or an invoice.

## Test with sample usage

Once a metered product uses the metric and a test contract includes its rate card, send two events and check the count. Use a contract with an open billing period and no other matching usage.

```bash Send one API call event
LAGO_URL="https://api.getlago.com"
API_KEY="__YOUR_API_KEY__"

curl --location --request POST "$LAGO_URL/api/v2/events" \
  --header "Authorization: Bearer $API_KEY" \
  --header 'Content-Type: application/json' \
  --data-raw '{
    "event": {
      "transaction_id": "api-call-test-001",
      "code": "api_calls",
      "external_contract_id": "contract_example"
    }
  }'
```

Send a second event with `transaction_id` set to `api-call-test-002`. The omitted `timestamp` defaults to the request time. Then read [contract current usage](/v2/guide/contracts/current-usage): the `api_calls_usd` entry should show `units` of `"2"`. Newly accepted events may take time to appear.

## Connect the metric to a metered product

When you create the API calls product, set `product_type` to `metered` and `billable_metric_code` to `api_calls`. Neither can change after the product is created. Keep the fixed `monthly_service` product separate: fixed products must not reference a metric.

## Update a metric

`PUT` and `PATCH /billable_metrics/{code}` accept partial updates. Once the metric is attached to a plan, only `name`, `description` and permitted filter changes are allowed. Changes to locked fields return `422`. Filter values referenced by product filters cannot be removed.
